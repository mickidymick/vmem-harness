0. What a reviewer needs to see

The original paper (VMem, MEMSYS 2025) proved the substrate is cheap — it gave every benchmark enough local memory to hold its whole footprint and measured only fault overhead. This paper makes a different claim: that VMem tiering actually works under a constrained DRAM budget. These are the questions a reviewer needs answered to believe it. Status reflects the run harness in vmem-sweep/phase1.sh.

1. How the three paths operate

Three paths move 2 MB pages between the tiers. They share a small set of containers, so work made by one is consumed by another — replication fills the eviction ring that demotion drains, and promotion borrows that same ring to make room. All three are on by default; disable one with its *_INTERVAL_MS=0.

The shared containers

free_dram / free_pmemfree-page pools, one per tier; the allocator draws DRAM from here first.
active_dram / active_pmemresident pages, one list per tier.
eviction_ringDRAM pages that already hold a PMEM replica — demotable with a pointer flip, no copy. Filled by replication; drained by demotion and by promotion’s room-making.
promotion_ringhot PMEM pages the sweep has queued to copy up.
vpte.replicaper page: pointer to a standby copy on the other tier (NULL if none). The invariant replica ≠ NULL ⇒ source is write-protected is what makes the flip safe.
vpte.invalidation_countwrites seen to a replicated page; a write drops the stale replica and bumps this.
vpte.dram_sinceresidency clock, stamped on every DRAM arrival; the grace window is measured against it.
Replication — prepay the copy

Background thread: copy a cold DRAM page down so it can later be demoted for free

every REPL_INTERVAL_MS→ pick a cold DRAM page
not recently written, past its grace window→ copy DRAM→PMEM
takes a free_pmem page→ set replica, write-protect the source→ enqueue in eviction_ring
REPL_INTERVAL_MS=200REPL_MAX_PER_TICK=256 REPL_INVAL_THRESH=4REPL_MIN_AGE_MS=1000
Demotion / eviction — flip the pointer

On demand: when the allocator needs DRAM and free_dram is empty

free_dram empty→ pop eviction_ring→ flip mapping onto the PMEM replica
no copy — the replica already exists→ return the freed page to free_dram

A write to a replicated page traps on the write-protect, drops the now-stale replica and bumps invalidation_count — so only clean pages are ever demoted for free.

EVICT_COLD_THRESH=64 (profiler build only)
Promotion — speculative, mirrors replication

Background thread: copy a hot PMEM page up, evicting a cold one to make room

every PROMO_INTERVAL_MS→ pick a hot PMEM page
by PROMO_HOT_METRIC→ queue in promotion_ring→ make room: take free_dram,
else evict a cold replica-backed page→ copy PMEM→DRAM under write-protect→ flip mapping, free the PMEM source, stamp dram_since

A concurrent write during the copy traps on the write-protect and lands on the new DRAM copy after the flip — the copy never tears.

PROMO_INTERVAL_MS=200PROMO_MAX_PER_TICK=64 PROMO_HOT_METRIC=fifoPROMO_HOT_THRESH=8

The metric is the open lever. fifo is a policy-free control — it treats every PMEM page as equally hot, so with tiering on by default it churns (a recent run promoted 2048 pages to serve a ~256-page hot set). llc and write need a profiler build; which one wins — and the best values for the intervals, batch sizes, and grace window — is what the knob sweep is for.

2. Migration runs at the single-threaded memcpy limit

VMem's own migration against what a bare memcpy achieves between the same two tiers.

There is no implementation inefficiency to find. Migration hits 107% of a single-threaded memcpy demoting and 92% promoting. The bottleneck is that the copy is single-threaded — and the headroom from parallelising it is wildly asymmetric: ~1.7× for demotion, ~8.4× for promotion.

Migration vs the memcpy baseline

baseline from ~/Projects/mlc, same machine, same 1 GiB size · 3 passes each

The comparison only means anything at matched thread counts. Against the 16-thread copy matrix VMem looks like it reaches 12% of “the hardware ceiling” — a dramatic and completely wrong conclusion, since VMem's copy is single-threaded. Worth stating before someone else derives it.

3. Replication turns migration into a pointer flip

Replicate a region to the other tier first, then migrate it.

Migration after replication is 156–235× faster, because there is nothing left to copy — the mapping is flipped onto a replica that already exists. The copy cost does not vanish; it moves off the critical path into the background replication thread.

Cost of the same 1 GiB move, with and without a replica

3 passes each · log scale — the two regimes are ~2.5 decades apart

The honest trade

Replication does not reduce total work — it roughly triples it. A prior eviction run replicated all 1536 pages but only evicted 512, so ~3 GB of background copying bought ~257 ms off the latency path. Good when DRAM pressure is bursty and bandwidth is idle; bad on a machine already bandwidth-saturated. VMEM_REPL_MAX_PER_TICK and VMEM_REPL_HOT_THRESH govern exactly this, and neither has been tuned.

5. Why any of this pays off: applications have a hot set

Migration and replication only earn their cost if the pages worth keeping in DRAM are few. Measured across six HPC and graph workloads — hardware LLC-miss sampling, tiering off, every page resident in DRAM so the profile is the application’s own, not the policy’s.

80% of last-level-cache misses fall in just 0.9–5.5% of an application’s resident memory. The hot set is tiny — exactly the regime where promoting a few pages beats the fifo churn from section 1 (2048 pages moved to serve a ~256-page hot set). BFS is the exception that proves the rule: its misses spread out — no decile below ~10% — so it has no hot set to promote, a workload tiering should leave alone.

Cumulative miss coverage vs. hot-set size

the hottest pages’ share of misses (y) against their share of resident footprint (x, log) · markers are measured deciles · sample_period 10000, 2 MB pages, tiering off

Read it as: the hottest X% of memory captures Y% of misses. A steep left edge is a sharp hot set; BFS (dashed) rises gradually and never concentrates. Curves begin at the 50% decile — the finest coverage the profiler reports — so they show the top of each distribution.

One profiler setting resolves every hot set: sample_period 10000. A 24-run sweep of the sampling rate showed the miss-rich workloads saturate far coarser and the miss-sparse ones (AMG, LULESH) converge exactly here; sampling denser only drops ring-buffer samples on the miss-rich workloads with no change to the answer. So the hot set can be found cheaply, with a single global rate rather than per-application tuning.

6. Locking the profiler interval: longer windows, stronger signal

The sample rate is locked; the other profiler knob is the analysis window. It has no effect on the cumulative hot set above — but the live policy decides from per-window counts, and a window must gather enough misses on a page to tell hot from cold. Same setup: tiering off, all DRAM, sample_period 10000; only the window varies.

Longer windows give a stronger, steadier signal — for the workloads that have a hot set to begin with. For the miss-rich workloads the hottest page’s per-window miss count climbs past a usable threshold by ~500 ms and keeps rising, and the per-window hot set holds steady. The miss-sparse workloads never get there: AMG, LULESH and BFS see only 2–6 misses on their hottest page at any window — too few to threshold, and too noisy to trust. A per-window policy simply cannot resolve them at this sample rate.

Per-window hottest-page miss count vs. window length

median over all windows in a run · both axes log · the dashed line is roughly the count a hot/cold threshold must sit above to discriminate

Read it as: how strong is the per-window hotness signal the policy sees? Miss-rich workloads (solid) cross into thresholdable territory around 500 ms; miss-sparse workloads (dashed) stay pinned near the noise floor no matter how long the window. Locked interval: 1000 ms — strong, stable per-window signal for every workload that has one, still one decision per second.

7. A second signal: sampling accesses, not just misses

The low-miss-rate workloads (AMG, LULESH, BFS) can’t be resolved by miss sampling at any window — their misses are hidden by the prefetcher. But those pages are still accessed. So we also sample MEM_INST_RETIRED.ALL_LOADS — every retired load, hit or miss — and attribute it to vpages the same way. Same window sweep, tiering off.

The access signal is the stronger, more universal one. It clears the thresholdable line for all six workloads where the miss signal clears it for only three — and it rescues the exact three that miss sampling gives up on (AMG’s hottest page: 2 misses vs 849 accesses per window). Where both work, they track each other. The miss signal keeps two jobs: it flags pages whose tier placement actually matters (a cache-resident hot page doesn’t need DRAM), and on churny workloads like Graph500 it reads steadier than the access signal, which faithfully — and noisily — tracks the moving frontier.

Top row (miss-rich): both signals rise together. Bottom row (miss-sparse): the miss line stays pinned at the noise floor while the access line climbs into usable range — often at far shorter windows. Open question: whether access-driven placement actually improves runtime, or over-promotes cache-resident pages, needs a tiering-on test.
